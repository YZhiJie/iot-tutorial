4.4.1 容错五层防线：对照 codec.ts 逐层拆解 ​

网络对端是不可信的：JSON 可能烂、字段可能缺、时间戳可能漂、报文可能重复。demo 的策略是一处收敛——所有容错集中在解码层，保证上层（store/UI）永远拿到干净数据，绝不让 UI 层散落容错逻辑。五层总览：

层拦截的坏数据demo 对策代码位置
解析容错烂 JSON、非对象载荷Result 风格 parseJsoncodec.ts
字段容错缺字段、NaN、字符串数字num() 清洗codec.ts
时间容错时钟漂移、缺失时间戳fixTs 钳制 + corrected 标记codec.ts
重复容错网络重发同 mid 报文markSeen 环形淘汰codec.ts
统计可观测——（以上所有层的出口）codecStats 计数上屏codec.ts + ConnectionIndicator.vue

第一层：解析容错。 JSON.parse 会抛异常，但更隐蔽的是"能 parse 却不是对象"：

ts
// 出处：demo/src/services/mqtt/codec.ts（节选）
function parseJson(raw: string): DecodeResult<Record<string, unknown>> {
  try {
    const v: unknown = JSON.parse(raw)
    if (!v || typeof v !== 'object' || Array.isArray(v)) {
      return { ok: false, reason: '载荷不是 JSON 对象' }
    }
    return { ok: true, value: v as Record<string, unknown> }
  } catch {
    return { ok: false, reason: 'JSON 解析失败' }
  }
}

第二层：字段容错。 字段可能缺失、可能是 "26.5" 这样的字符串、也可能是 NaN：

ts
// 出处：codec.ts（节选）
// 数值字段清洗：字符串数字兜底转换，其余非有限数一律剔除，绝不让 NaN 流入 UI
function num(v: unknown): number | undefined {
  if (typeof v === 'number' && Number.isFinite(v)) return v
  if (typeof v === 'string' && v.trim() !== '' && Number.isFinite(Number(v))) return Number(v)
  return undefined
}

第三层：时间容错。 设备时钟不可信。demo 的策略是"容忍轻微漂移、钳制大漂移、全程打标"：

ts
// 出处：codec.ts（节选）
// 时间戳漂移容忍：偏差超过 5 分钟视为设备时钟异常，钳制为本地接收时间
const MAX_TS_DRIFT_MS = 5 * 60 * 1000
function fixTs(raw: unknown, recvTs: number): { ts: number; corrected: boolean } {
  const ts = num(raw)
  if (ts === undefined) return { ts: recvTs, corrected: true }
  if (Math.abs(ts - recvTs) > MAX_TS_DRIFT_MS) return { ts: recvTs, corrected: true }
  return { ts, corrected: false }
}

第四层：重复容错。 模拟器约 6% 概率原样重发上一条（mid 相同），真实世界对应 QoS 1 重传与设备重启后补发。demo 用 Set + 队列模拟定容去重：

ts
// 出处：codec.ts（节选）
const DEDUPE_CAP = 500
function markSeen(id: string): boolean {
  if (seenMids.has(id)) return false
  if (midQueue.length >= DEDUPE_CAP) {
    const oldest = midQueue.shift() // 环形淘汰最旧 id，容量恒定
    if (oldest !== undefined) seenMids.delete(oldest)
  }
  midQueue.push(id)
  seenMids.add(id)
  return true
}

不可观测的容错等于没做。 容错层的本职就是"安静地吃掉坏数据"，若没有计数，你永远不知道它今天吃了多少、哪类坏数据在变多、是不是某批固件开始发烂报文了。五个计数把"静默吞噬"变成"可视化的健康指标"——丢弃率突然从 1% 跳到 20%，就是设备端事故的最早信号。

4.4.2 降级、空态与前端规则引擎 ​

三类空态设计。 容错解决"数据脏"，空态解决"数据还没有"：

  • 等待档案空态：设备档案走 retained status（见 4.3），订阅瞬间即达；但 broker 重启且设备尚未重连的窗口期，档案确实缺席。此时设备列表不应空白或报错，而应显示"等待设备注册…"的骨架态；
  • 图表无数据：TelemetryChart 对空窗渲染空坐标系（win = e?.window ?? []），坐标轴都在、曲线为空——用户能看出"连着但没数据"，而不是白屏误会页面坏了；
  • 离线卡片置灰：长期离线的设备（demo 的 gh01-004，retained status=offline）必须"在列表里但置灰"。让离线设备消失是灾难性设计——用户会以为整系统挂了；置灰 + 离线原因（reason: maintenance）才是诚实的呈现。

前端规则引擎：双通道告警的取舍。 demo 的告警中心有三路来源（见 alerts.ts 注释）：A 设备事件（up/event，如设备自判的 TEMP_HIGH）、B 前端本地推导（离线看门狗的 DEVICE_OFFLINE）、C 平台规则引擎（预留接口）。双通道各有优劣：

  • 设备规则（阈值判定在设备侧）：离现场近、零延迟、断网也能判定；但规则改动要刷固件，算力受限的设备跑不了复杂规则；
  • 前端/平台规则：集中可配置、可跨设备关联；但受消息延迟影响，且断线时失效。

demo 的分工原则值得记住：前端只做"设备做不了的事"。阈值告警交给设备（它有最准的现场读数），前端负责离线推导（设备自己离线了没法报自己）。这样职责单一，天然避免了"双份打架"——同一高温事件不会同时出现"设备 TEMP_HIGH"和"前端阈值告警"两条记录。确需双通道并存时，用 alerts.ts 的冷却机制（同 deviceId:code 60 秒冷却）兜底去重，并在设计阶段就画一张"规则归属表"：每类告警有且只有一个权威来源。

4.4.3 错误上报与监控埋点 ​

单屏的 codecStats 解决"看得见"，生产还需要"收得回"。最小埋点集只有三个指标，全部来自 demo 已有的状态：

ts
// 生产扩展示例（demo 未实现）：最小监控埋点接口（不绑定具体 SDK）
interface MonitorPayload {
  reconnectCount: number // 会话内累计重连次数（connection store 的 attempt 累计）
  dropRate: number // 解码丢弃率 = codecStats.dropped / codecStats.received
  commandTimeoutRate: number // 指令超时率 = timeout 次数 / 下发总次数
  ts: number
}

function report(payload: MonitorPayload): void {
  // 上报通道自定：sendBeacon / 复用 MQTT 上报 / 接入层采集均可；
  // Sentry 一类平台可映射为自定义事件上报
  navigator.sendBeacon('/api/monitor', JSON.stringify(payload))

三条设计纪律：

  • 聚合后上报，绝不逐条上报：遥测是高频流，逐条埋点等于用监控流量复刻一条数据通道；固定窗口（如每分钟）聚合一次再发；
  • 坏样本要带上下文：上报丢弃率的同时，抽样携带 reason 与 topic（如"JSON 解析失败 @ iot/gh01/gh01-002/up/telemetry"），否则收到告警也无法定位是哪批设备；
  • 指标对应行动：重连次数涨 → 查网络或 Broker 稳定性；丢弃率涨 → 查设备固件；指令超时率涨 → 查设备响应或 QoS 链路。没有对应处理预案的指标不必上报。

Sentry 一类平台的集成思路（不展开具体 SDK 细节）：把 codecStats 五计数、重连 attempt、指令三态结果映射为平台的自定义事件与上下文标签，使"前端容错层的运行状况"成为可检索、可聚合、可告警的一等公民； sourcemap 上传让压缩后的报错能还原到源码行。平台选型不重要，重要的是"容错层的运行状况被持续采集"这件事本身。

4.4.4 生产落地总清单与上线策略 ​

总清单（28 条） ​

安全（对应 4.1）

  • [ ] 前端连接走 wss，TLS 证书由正规 CA 签发并监控有效期
  • [ ] 连接凭证为短期 token/票据，前端代码与存储中无长效密钥
  • [ ] Broker 配置 Topic 级 ACL：设备/前端按 4.1.3 权限表收敛，含兜底 deny
  • [ ] clientId 含随机成分且与认证绑定，可预测 id 不可连接
  • [ ] CSP connect-src 显式列出全部 wss 连接源
  • [ ] pnpm-lock.yaml 入库，CI 使用 frozen-lockfile 安装，私有源固定

性能（对应 4.2）

  • [ ] 遥测滑窗有上限（demo 120 点），长会话内存平稳（双快照验证）
  • [ ] 图表批量渲染（≥500ms 间隔），绝不逐消息 setOption
  • [ ] 告警有冷却窗口（demo 60s）与容量上限（demo 200 条）
  • [ ] ECharts 按需注册（echarts/core），无 1MB 级 chunk 体积警告
  • [ ] 设备列表在千级规模启用虚拟列表
  • [ ] Performance 录制验证无 >50ms 长任务，基线数据留档

可靠性（对应 4.3）

  • [ ] 重连采用全抖动指数退避并 30s 封顶，attempt 成功归零
  • [ ] 重连成功后显式 resubscribe，恢复后数据持续到达
  • [ ] 入站看门狗覆盖"无 close 的假死"场景
  • [ ] 设备离线三重保障：status 自报 / 遗嘱消息 / 前端看门狗
  • [ ] 指令下发有超时语义（demo 8s）与 ok/rejected/timeout 三态结果
  • [ ] 关键档案依赖 retained 保留消息，并有重连对账兜底

可观测（对应 4.4.1 / 4.4.3）

  • [ ] codec 五类计数（received/decoded/dropped/duplicates/corrected）上屏
  • [ ] 连接状态机五态可视化，重连次数可见
  • [ ] 重连次数/丢弃率/指令超时率聚合上报并有告警阈值
  • [ ] 坏报文样本可按 reason 与 topic 聚合定位
  • [ ] 监控埋点聚合上报，不逐条上报遥测

合规与工程（跨章）

  • [ ] 敏感字段（IP/位置）展示层脱敏
  • [ ] localStorage 只存非敏感覆盖项，用户可一键清除
  • [ ] payload 契约带版本字段（见下文 v 字段方案）
  • [ ] 指令下发有审计痕迹（谁在何时对哪台设备下发了什么）
  • [ ] 每类告警有唯一权威来源（规则归属表）
  • [ ] 应用卸载钩子清理全部定时器与连接（防泄漏）

上线策略 ​

灰度：按产品/设备分批切流（先 1 个产品 → 10% → 全量），每一批观察丢弃率与重连次数相对基线的变化——这两个指标是"新版本是否破坏了数据链路"的最早信号。

回滚：前端静态资源多版本共存，可秒级切回上一版；Broker 的 ACL/认证配置变更保留上一版本文件，回滚即重载。回滚演练要在灰度前做一次，真出事时才不会手忙脚乱。

契约版本兼容：设备固件永远参差不齐，payload 从第一天就要带版本字段：

运行与验证 ​

对照模拟器的脏数据剧本（见 simulator.mjs 头部注释），逐个验证 codecStats 计数的语义：

  1. 启动 pnpm server，打开前端，运行 2 分钟；
  2. duplicates 增长：模拟器传感器与插座剧本都以约 6% 概率原样重发上一条（mid 相同）——观察计数稳定爬升，同时 dropped 同步增长（重复计入丢弃）；
  3. corrected 不增长（容忍语义）：低功耗设备 gh01-002 每 15 秒批量上报 4 个样本，带 +90 秒时钟偏移——在 ±5 分钟容忍区间内，时间戳保留设备原值，corrected 不动；
  4. corrected 增长（钳制语义）：临时把 codec.ts 的 MAX_TS_DRIFT_MS 改成 30_000 并刷新，gh01-002 的批量样本立刻被判漂移、钳制为接收时间，corrected 开始增长；验证完改回；
  5. 上屏一致性：ConnectionIndicator 底部"解析 X · 丢弃 Y"与 codecStats 实时一致。

运行方式：cd demo && pnpm server，浏览器打开 http://localhost:5173 观察约 2 分钟并对照以上五步

最佳实践与常见坑 ​

坑 1：容错逻辑吞错无声 现象：用户反馈"数据时有时无"，但控制台零报错、日志零异常，排查无门。 原因：容错层把坏数据静默丢弃了——它太尽职了，尽职到没人知道它在工作。 解法：每个丢弃分支必须计数且 reason 可区分（demo 五计数 + DecodeResult 的 reason 字段）；丢弃率纳入监控（4.4.3 埋点）；开发期可临时在 dropped 增长时 console.warn 抽样打印原始载荷。

坑 2：清空 retained 后，前端永远等不到档案 现象：设备遥测曲线正常滚动，但列表里名称全是裸设备 id、产品信息缺失。 原因：设备档案只在上线时 retain 发布一次；Broker 的 retained 数据被清空（demo 的 aedes 是内存实现，重启即清空，靠模拟器重连重发来补救）而设备不再重连时，前端没有任何途径拿到档案。 解法：生产环境档案走持久化存储 + REST 快照对账（4.3 的生产扩展）；或要求设备周期性重发 retained status（档案随心跳携带）；运维清理 retained 前先评估对依赖方的影响。

坑 3：告警规则与设备规则双份打架 现象：同一高温事件产生两条告警（设备 TEMP_HIGH + 前端阈值告警）；或两条告警先后出现、结论互相矛盾，用户不知道信谁。 原因：同一规则在设备侧和前端各实现了一份，两边的阈值/数据/时机还可能不一致。 解法：设计期先画"规则归属表"，每类告警唯一权威来源；前端只做设备做不了的事（如离线推导，demo 的分工）；确需双通道时以冷却去重兜底（alerts 的 60s 冷却），并在文案中标注来源（fromDevice 字段）。
