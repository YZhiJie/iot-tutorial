第 3.2 章 设备列表管理 ​

  • 前置知识：第 3.1 章（环境已能启动、Topic 契约总表）、Pinia setup store 基础写法
  • 预计学习时长：约 35 分钟
  • 配套代码：
    • demo/server/simulator.mjs（设备档案的发布方）
    • demo/src/types/iot.ts（契约类型定义）
    • demo/src/stores/devices.ts（设备注册表）
    • demo/src/views/DeviceListView.vue（列表视图）
    • demo/src/components/DeviceCard.vue（设备卡片）
    • demo/src/components/StatusBadge.vue（在线徽标）
  • 本章实操任务：1 项

打开 IoT Deck 的第一眼是设备列表：8 张卡片、统计条、搜索框。看似只是"读个接口渲染列表"的普通页面，但在这个项目里，列表数据不是一次性拉来的，而是从消息流里"长"出来的。本章讲清三件事：设备档案如何注册进前端、注册表数据结构如何设计、视图层如何只做派生不存副本。

学习目标 ​

  • 理解 retained 状态消息如何实现"订阅瞬间即收全量设备清单"，以及遗嘱消息（LWT）的作用；
  • 掌握 DeviceEntry 注册表设计：ensure 惰性建项、profile 为何允许为空；
  • 学会视图层的"派生不存储"原则：搜索、过滤全部用 computed，不在 store 里存第二份；
  • 完成"按产品类型筛选"的实操扩展。

设备档案的注册机制：retained status 一次拿全量 ​

先想一个经典难题：前端晚于设备上线（比如你刷新了页面），怎么知道现在有哪些设备？

方案 A：前端向服务端要设备清单——这要求额外做一个 HTTP 接口，两条链路、两套状态同步，麻烦。方案 B：利用 MQTT 保留消息——每台设备上线时把"设备档案"以 retain 模式发布到 up/status，Broker 会为每个主题保存最后一条保留消息；之后任何订阅者一订阅就立刻收到它，无需等待下一次上报。IoT Deck 采用方案 B。

看模拟器的发布方实现（demo/server/simulator.mjs）：

js
// 文件: demo/server/simulator.mjs（节选）
const client = mqtt.connect(BROKER_URL, {
  clientId: `dev-${def.id}`,
  clean: true,
  keepalive: 30,
  reconnectPeriod: 3000,
  // 遗嘱（LWT）：连接异常断开时由 Broker 代发 retained 离线状态
  will: {
    topic: `${base}/up/status`,
    payload: JSON.stringify({ online: false, reason: 'connection_lost' }),
    qos: 1,
    retain: true,
  },
})

client.on('connect', () => {
  // 上线即注册"设备档案"（保留消息）：前端订阅后立刻收到，无需等下一次上报
  publish(
    client,
    `${base}/up/status`,
    {
      online: true,
      name: def.name,
      product: { id: productId, name: PRODUCT_NAMES[productId] },
      fw: 'v1.4.2',
      ip,
    },
    { qos: 1, retain: true },
  )

  if (def.mode === 'offline') {
    // gh01-004 的剧本：注册为长期离线后直接断开
    publish(client, `${base}/up/status`, { online: false, reason: 'maintenance' }, { qos: 1, retain: true })
    client.end()
    return
  }
  // …
})

三个细节值得咀嚼：

  1. retain: true 是关键。没有它，"刷新页面 → 档案消失"——因为档案只在设备上线那一瞬发布过一次；有了它，Broker 替每台设备记住最新档案，前端任何时候订阅都能"秒收全量"。
  2. 遗嘱消息是离线兜底。设备如果拔网线/断电，来不及发布离线状态，Broker 检测到连接异常断开会代发遗嘱 {online:false, reason:'connection_lost'}，同样是 retained——在线状态永远有"最后一句遗言"。
  3. gh01-004 是刻意设计的离线样本：它发布 retained 的 status=offline 后直接 client.end()，所以列表上它永远灰着。这是你验证"retained 离线"的测试桩。

再看前端的接收方。up/status 报文经网关路由到 store 的 ingestProfile（demo/src/stores/devices.ts）：

ts
// 文件: demo/src/stores/devices.ts（节选）
/** 设备档案（up/status 保留消息）：首次订阅即可获得全部设备清单 */
function ingestProfile(deviceId: string, productId: string, s: DecodedStatus): void {
  const e = ensure(deviceId)
  e.profile = {
    productId,
    productName: s.productName || productId,
    deviceId,
    name: s.name || deviceId,
    fw: s.fw,
    ip: s.ip,
  }
  setOnline(e, s.online, s.reason)
}

DeviceEntry 注册表设计：ensure 惰性建项与可空 profile ​

store 的核心数据结构是一个 Record<deviceId, DeviceEntry>。为什么不用数组？消息流是按 deviceId 高频写入的——每条遥测都要定位到对应设备，Record 的键访问是 O(1)，数组则要 find 遍历。列表展示需要数组？用 getter 派生即可，不必维护两份结构。

ts
// 文件: demo/src/stores/devices.ts（节选）
export interface DeviceEntry {
  profile: DeviceProfile | null
  online: boolean
  /** 最近一次"收到消息"的本地时间（用接收时刻而非设备 ts，天然免疫时钟漂移） */
  lastSeenAt: number
  latest?: TelemetryPoint
  /** 遥测滑动窗口（时间升序），上限 windowCap */
  window: TelemetryPoint[]
  tempThreshold: number
  /** 智能插座开关状态 */
  on?: boolean
  offlineAlerted: boolean
}

export const useDevicesStore = defineStore('devices', () => {
  const map = ref<Record<string, DeviceEntry>>({})

  function ensure(deviceId: string): DeviceEntry {
    let e = map.value[deviceId]
    if (!e) {
      e = {
        profile: null,
        online: false,
        lastSeenAt: 0,
        window: [],
        tempThreshold: CONFIG.defaultTempThreshold,
        offlineAlerted: false,
      }
      map.value[deviceId] = e
    }
    return e
  }
  // …
})

两个设计决策：

决策一：ensure 惰性建项。任何消息入口（档案、遥测、事件）都不必先问"这个设备存在吗"，直接 ensure(deviceId) 拿到条目再写入。消息驱动系统里"先建项后写入"的显式顺序很难维持——ensure 把建项时机下沉到第一次数据到达，天然不会漏。

决策二：profile 允许为 null。为什么不把 DeviceProfile 设为必有字段？因为遥测可能先于档案到达：MQTT 不保证不同主题的消息按"你期望的顺序"投递——设备先发了一条遥测、档案还在路上（或档案的 retained 消息因故未收到），这时遥测总不能被扔掉。所以注册表条目先以 profile: null 存在，档案到了再补齐。配套的兜底写在遥测入库里：

ts
// 文件: demo/src/stores/devices.ts（节选）
function ingestTelemetry(deviceId: string, _productId: string, points: TelemetryPoint[]): void {
  if (points.length === 0) return
  const e = ensure(deviceId)
  if (!e.online) {
    // 即使设备从未发过 status，只要遥测到达即视为在线（status 报文丢失的兜底）
    e.online = true
    e.offlineAlerted = false
  }
  // …
}

视图实现：派生筛选与产品差异化卡片 ​

视图层 (demo/src/views/DeviceListView.vue) 没有一行"初始化列表"的代码，它只做三件事：派生统计、派生筛选、渲染卡片。

vue
<!-- 文件: demo/src/views/DeviceListView.vue（节选） -->
<script setup lang="ts">
const devices = useDevicesStore()
const keyword = ref('')
const filter = ref<'all' | 'online' | 'offline'>('all')

const filtered = computed(() =>
  devices.list.filter((e) => {
    const name = `${e.profile?.name ?? ''} ${e.profile?.deviceId ?? ''}`.toLowerCase()
    if (keyword.value && !name.includes(keyword.value.trim().toLowerCase())) return false
    if (filter.value === 'online' && !e.online) return false
    if (filter.value === 'offline' && e.online) return false
    return true
  }),
)
</script>

<template>
  <p class="page-sub">
    共 {{ devices.list.length }} 台 · 在线 {{ devices.onlineCount }} · 离线
    {{ devices.offlineCount }} · 未读告警 {{ alerts.unreadCount }}
  </p>
  <div class="toolbar">
    <input v-model="keyword" class="input" placeholder="搜索设备名称 / ID…" />
    <select v-model="filter" class="input select">
      <option value="all">全部设备</option>
      <option value="online">仅在线</option>
      <option value="offline">仅离线</option>
    </select>
  </div>
  <div v-if="filtered.length" class="card-grid">
    <DeviceCard
      v-for="e in filtered"
      :key="e.profile?.deviceId ?? '?'" :entry="e" :now="now"
      @click="router.push(`/devices/${e.profile?.deviceId ?? ''}`)"
    />
  </div>
  <div v-else class="empty-state">没有匹配的设备（等待设备上报档案中…）</div>
</template>

注意三个"派生"：

  • 统计条不存副本：devices.onlineCount、offlineCount 是 store 里的 computed（list.value.filter(e => e.online).length），基于同一份 map 派生，永不会与实际状态不同步；

  • 跳转用 router.push：卡片整体可点击，/devices/:deviceId 路由带 props: true 把 deviceId 传给详情页（路由定义见 src/router/index.ts）。

卡片组件 (demo/src/components/DeviceCard.vue) 面对的难点是产品差异化：传感器报温湿度电量，插座报功率电压开关。用一个 metrics 计算属性按 productId 收敛成统一结构，模板只认 Metric[]：

vue
<!-- 文件: demo/src/components/DeviceCard.vue（节选） -->
<script setup lang="ts">
const props = defineProps<{ entry: DeviceEntry; now: number }>()

interface Metric {
  label: string
  value: string
}

const metrics = computed<Metric[]>(() => {
  const l = props.entry.latest
  if (!l) return []
  if (props.entry.profile?.productId === 'pl01') {
    return [
      { label: '功率', value: `${fmtNum(l.power, 0)} W` },
      { label: '电压', value: `${fmtNum(l.voltage, 0)} V` },
      { label: '开关', value: l.on ? '开' : '关' },
    ]
  }
  return [
    { label: '温度', value: `${fmtNum(l.temp, 1)} ℃` },
    { label: '湿度', value: `${fmtNum(l.humi, 0)} %RH` },
    { label: '电量', value: `${fmtNum(l.battery, 0)} %` },
  ]
})

const title = computed(() => props.entry.profile?.name ?? props.entry.profile?.deviceId ?? '(等待设备档案)')
</script>

运行与验证 ​

按 3.1 章启动两个终端后，逐项验证：

  • [ ] 8 张卡片出现：打开列表页，共 8 台（6 传感器 + 2 插座），统计条显示"共 8 台 · 在线 7 · 离线 1"。卡片出现可能比页面打开晚 1 秒内——那是 retained 档案回放的耗时。
  • [ ] gh01-004 显示离线："育苗棚 C1 · 温湿度"始终灰色。对照终端 1 日志能看到它注册离线的一行：[device] gh01-004 注册为长期离线（retained status=offline）。刷新页面它依然是离线——retained 消息在起作用。
  • [ ] 搜索过滤生效：输入"泵房"只剩 2 张插座卡片；输入设备 ID 片段"gh01-00"剩 5 张传感器；切到"仅离线"只剩 gh01-004。清空输入后 8 张全部恢复——确认没有出现"过滤后数据覆盖了原始列表"。
  • [ ] 卡片跳转详情：点击任意在线传感器卡片，URL 变为 /devices/gh01-001 形态，进入详情页（曲线相关内容是 3.3 章主题）。浏览器后退回到列表，筛选关键词仍保留——因为 keyword 是组件内 ref，后退重进组件会重置，这是预期行为。
  • [ ] （对照实验）：在终端 1 按 Ctrl+C 停掉服务端约 50 秒后，所有设备陆续被前端看门狗推导为离线（徽标变灰、统计条离线数上涨）——这就是 lastSeenAt 超时推导在工作。

最佳实践与常见坑 ​

坑 1：档案未到就渲染，空指针炸页面

  • 现象：页面偶发白屏，控制台报 Cannot read properties of null (reading 'name')，多发生在刚打开页面的一瞬间。
  • 原因：profile 是可空字段（遥测可能先于档案到达，见正文），组件里直接写 entry.profile.name 就是踩空。
  • 解法：全链路可选链 + 兜底文案。参考 DeviceCard 的写法：标题 profile?.name ?? profile?.deviceId ?? '(等待设备档案)'，模板里 entry.profile?.fw 配合 v-if。原则是任何访问 profile 字段的地方都必须经过 ?. 或已判空——因为 null 不是异常路径，是设计内状态。

坑 2：把搜索结果存进 store，造成双份状态

  • 现象：初级实现常写成 watch(keyword, v => store.searchedList = filterList(v))。之后出现诡异 bug：消息流新设备上线，搜索结果不更新；或清空关键词后列表少设备。
  • 原因：store 里同时存了全量 list 和过滤后的 searchedList，两份状态。任何写入方（消息流、筛选、清空）只更新其一，两者必然漂移——双份状态没有唯一事实源。
  • 解法：视图层的过滤一律 computed 派生，绝不过渡存储。像 demo 那样：store 只存真值（map），搜索词只是组件内 ref，filtered computed 把两者 join 出展示结果。派生数据永远正确，因为它每次都从真值现算。

坑 3：用数组下标当 key，列表复用错位

  • 现象：卡片内容"串门"——A 卡片显示了 B 设备的指标，或过渡动画错乱。
  • 原因：v-for="(e, i) in filtered" :key="i" 时，Vue 按下标复用 DOM。消息驱动列表的顺序和数量随时变化（新设备插入、过滤条件改变），下标 i 对应的设备换了人，组件状态（过渡、聚焦）被错误地留给新主人。
  • 解法：用业务唯一标识 :key="e.profile?.deviceId ?? '?'"（demo 即如此）。档案未到时兜底 '?' 只是短暂瞬态；更好的做法是过滤前先按 profile 是否存在分桶。核心原则：key 必须稳定且与数据实体一一对应，与渲染顺序无关。

坑 4：在线判定只信设备自报，"静默离线"永远在线

  • 现象：设备拔电后（遗嘱也因网络分区未送达），列表徽标一直是绿的，曲线却停在上报中断那一刻。
  • 原因：只消费 up/status 的 online 字段，而 status 是低频消息，"不再说话的设备"不会主动告诉你它死了。
  • 解法：引入看门狗。demo 的 startWatchdog 每 5 秒扫一遍注册表，lastSeenAt 超过 CONFIG.offlineAfterMs（45 秒）即推导离线并推送告警。记住口诀：自报状态管"宣告"，lastSeen 管"事实"。

实操任务 ​

任务：新增"按产品类型筛选"下拉

在现有"全部/仅在线/仅离线"下拉旁，增加一个按产品类型筛选的选择器：全部类型 / 传感器（gh01）/ 插座（pl01）。

实现提示：

  1. 新增组件内状态 const productFilter = ref<'all' | 'gh01' | 'pl01'>('all')，模板复制一个 <select>（选项文案：全部类型 / 温湿度传感器 / 智能插座）；
  2. 扩展 filtered computed，加一条判断：if (productFilter.value !== 'all' && e.profile?.productId !== productFilter.value) return false；
  3. 注意 e.profile?.productId 可空——设备档案未到时它属于哪个产品是未知的，想想这类设备在"传感器"筛选下应不应该出现（建议：归入"全部"可见，产品筛选非 all 时隐藏，因为无法归类）。

验证：选择"智能插座"应只剩 2 张泵房卡片；此时终端 1 若重启服务端（模拟器重发档案），列表应保持筛选状态自动恢复正确结果——这正是 computed 派生的红利。
