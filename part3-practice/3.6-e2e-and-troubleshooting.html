第 3.6 章 联调验收与问题排查 ​

  • 前置知识：第 3.1~3.5 章全部内容（连接、遥测、指令、告警）、浏览器 DevTools 基本用法
  • 预计学习时长：约 40 分钟
  • 配套代码：
    • demo/src/services/mqtt/topics.ts（订阅清单：实操演练的「病灶」）
    • demo/src/services/mqtt/index.ts（route 路由：断点位置）
    • demo/src/services/mqtt/codec.ts（解码统计计数器）
    • demo/server/broker.mjs（Broker 观察性日志）
    • demo/server/simulator.mjs（设备侧实现与故障剧本）
  • 本章实操任务：1 项（人为制造订阅故障，用排查表定位并恢复）

学习目标 ​

  • 掌握一套可复用的端到端验收清单，能独立判断「这个 IoT 监控台是否正常工作」；
  • 面对故障能按「现象 → 可能原因 → 定位手段」的结构化思路收敛，而不是盲目试错；
  • 熟悉四件调试工具：DevTools WS 帧面板、server 日志对照、网关路由断点、命令行订阅观察；
  • 建立「数据流分段定位」的意识：设备 → Broker → 前端，先找断点在哪一段。

3.6.1 端到端验收清单 ​

联调验收不是「页面能打开」，而是把系统的每个能力都走一遍。以下 13 条基于本 demo 的设备剧本设计，全部通过才算验收完成。

建议按顺序分组执行：第 1~2 条验「连接与档案」，第 3~5 条验「数据接收」，第 6~7 条验「远程控制」，第 8~9 条验「告警」，第 10~13 条验「容错与恢复」——前面的组失败时，先修好再往下走，否则后面的现象全是噪音。

  • [ ] 连接指示器为绿色「已连接」，下方「解析 / 丢弃」计数持续增长（数据在流）
  • [ ] 设备列表出现 8 张卡片：gh01-001 ~ gh01-006 + pl01-001 / pl01-002
  • [ ] gh01-004 始终显示离线（长期离线剧本：retained status = offline，原因 maintenance）
  • [ ] 低功耗设备 gh01-002 的曲线每 15 秒一次跳 4 个点（批量信封剧本），而非连续平滑
  • [ ] 进入设备详情，曲线随时间滚动推进，窗口超过 120 点后旧点被裁剪
  • [ ] 插座开关：点「关闭插座」→ 日志「成功 · 开关已关闭」→ 功率曲线落到 0W；再打开回执「开关已打开」、功率回到 1200W 附近
  • [ ] 重启设备：卡片短暂离线（rebooting）→ 约 2.5s 恢复在线 → 日志「成功 · 设备已完成重启」
  • [ ] gh01-003 温度尖峰出现时，全局 error 横幅自动弹出
  • [ ] 告警中心按「仅 error」筛选有效；确认处置后未读计数归零、横幅消失
  • [ ] 杀掉 pnpm server 进程 → 指示器变黄「重连中（第 N 次）」持续递增
  • [ ] 重新执行 pnpm server → 前端自动恢复连接，8 张卡片档案重新出现，数据继续流动
  • [ ] 设备离线或连接断开时，控制面板按钮禁用并显示提示文案
  • [ ] 长会话（10 分钟以上）运行后，「解析 / 丢弃」计数趋于平稳，页面操作无明显卡顿（性能粗查）

其中第 10、11 条值得展开：前端重连由 MqttConnection 的全抖动指数退避驱动（delay = random(0, min(30s, 1s × 2^attempt))），所以重连不是等间隔的；恢复依赖模拟器重新接入后重发 retained 档案，加上前端重连成功后显式重订阅（clean 会话不保留订阅列表）。三者缺一，自动恢复就不成立。

3.6.2 故障排查大表 ​

排查 IoT 故障的核心方法是分段定位：一条数据从设备到曲线要过三段（设备/模拟器 → Broker → 前端解码与 store），先确认断在哪一段，再查段内细节。下表是本 demo 最常见的八类故障：

现象可能原因定位手段
一直「连接中…」或「重连中」broker 未启动；MQTT URL 配错；WS 路径不是 /mqttConsole 找 [mqtt] 连接错误 日志；核对 .env.development 的 VITE_MQTT_URL 与 localStorage 覆盖键 iot.mqttUrl；确认 server 日志里 1883/8083 已就绪
已连接但收不到任何数据订阅通配符写错；两端 Topic 契约不一致server 日志看有无 iot/ 报文发布（有→前端订阅问题，无→设备侧问题）；对照 SUBSCRIBE_TOPICS 与模拟器发布主题
卡片不出现或无档案信息retained 档案未发布/被清空（broker 重启且模拟器未重连）；up/status 不在订阅范围；档案 JSON 解析失败被丢弃命令行订阅 iot/+/+/up/status 看有无保留消息；看「解析/丢弃」计数是否异常增长
曲线不动store 有数据但图表 800ms 定时刷新有延迟感；设备批量稀疏上报（gh01-002 每 15s 4 点）；后台标签页被浏览器节流Vue DevTools 看 devices store 的 window 数组是否增长；切回前台观察是否补渲染
指令总是「超时」设备实际离线；回执主题拼错（两端 command_reply 不一致）；模拟器未订阅 down/commandserver 日志看 [device] xxx 收到指令；命令行订阅 iot/+/+/down/command_reply 看回执是否发出、载荷是否完整
回执发出但 Promise 不落定id 不匹配：模拟器回执的 id 与请求 id 不一致，pending 查不到被静默丢弃server 日志打印了 id 前 8 位（收到指令 switch (id=xxxx)），与前端 onCommandReply 日志逐条对照
告警不弹60s 冷却窗口拦截同设备同 code 的后续告警；告警中心级别筛选过滤掉了；warn 不弹横幅（latestUnackedError 只认 error，属设计）告警中心切「全部级别」；对照时间线确认是否落在冷却窗口内
重复报文计数持续偏高模拟器刻意制造的 6% 重发剧本（mid 相同，前端应去重）——这是预期行为观察丢弃计数增长但曲线无重复毛刺，说明 codec 去重生效，无需处理
频繁掉线重连（重连风暴）clientId 冲突互踢（MQTT 规定同 id 后连踢前连）；重连退避未随机化，服务端重启后全体客户端同时冲击broker 日志看同一 clientId 反复「接入 + / 断开 -」；确认 clientId 含随机后缀、退避用全抖动（对照 connection.ts）

读这张表的方法：先锁定最精确的现象（越具体越好，「曲线不动」不如「gh01-002 曲线不动」好定位），再从上往下排除原因，每一项都用可观测的手段证实或证伪，而不是改一行代码碰运气。

排查示范：一次「指令超时」的完整动线 ​

空谈不如走一遍。假设现象是：对 pl01-001 点「打开插座」，指令日志 8 秒后显示「超时」。按分段定位的思路走：

第 1 步：确定断点在哪一段。 三处证据依次取：

  • 浏览器 WS 帧面板 → 有没有 down/command 的出站帧？（有 → 前端已发出；没有 → 查前端，比如连接状态不对）
  • server 终端 → broker 日志里有没有对应的转发记录？（broker 收到才会打印）
  • server 终端 → [device] pl01-001 收到指令 switch (id=xxxx) 在不在？
text
[broker] web-console_a1b2c3d4 → iot/pl01/pl01-001/down/command (58B, qos1)   ← broker 收到并转发
（缺：[device] pl01-001 收到指令 …）                                          ← 设备侧没收到/没处理
1
2

第 2 步：段内定位。 断点在「模拟器收报文」这一段。可能原因按排查表：设备离线？——不是，卡片在线；订阅丢了？——模拟器只在 connect 回调里订阅一次，若它重连过且订阅失败就会哑掉。看 server 日志里模拟器最近的「接入 + / 断开 -」记录即可证实。

第 3 步：修复与回归。 重启 pnpm server 让模拟器重新接入订阅，重发指令验证回执正常，最后把这次故障的「现象 / 根因 / 修法」记进团队的排查文档。

注意整条动线没有一行「猜」的成分：每一跳都有日志或帧证据。养成这个习惯，联调效率会比「改一版试一下」高一个数量级。

附：Console 报错文本速查 ​

前端日志里的关键报错文本都是代码里写死的，可以直接反查出处：

Console 报错出处与含义
WebSocket connection to 'ws://localhost:8083/mqtt' failed连不上 Broker：进程没起、端口错、或路径不是 /mqtt
[mqtt] 连接错误：…mqtt.js 的 error 事件（connection.ts 打印）；它之后通常紧跟 close，真正原因常要看 broker 日志
[mqtt] 订阅失败subscribe 回调返回 err：重订阅没成功，此刻连接虽在但收不到数据
[device] xxx 指令解析失败模拟器侧：收到的指令载荷不是合法 JSON 或字段缺失
[gateway] 指令回执 {…}useIot 里保留的全局回执日志：核对 id 与 ok 字段就靠它
IoT 网关尚未启动getGateway 在 start() 之前被调用——装配时序问题，查调用时机

另有一个不是报错但最常见的「静默失败」：什么都没打印、数据也不来——那是 parseTopic 返回 null 后 route 静默 return 了。遇到「无日志、无数据」，第一反应就应该是主题没匹配上契约。

3.6.4 性能粗查 ​

IoT 监控台是长会话应用，性能问题往往是「开一小时后变卡」型的。开发阶段就做一次粗查，操作与判读各三步：

操作步骤：

  1. DevTools → Performance 面板 → 点录制 → 正常操作页面 10 秒（切详情、开合插座、看告警）→ 停止录制；
  2. 顶栏看 FPS 轨道与主线程火焰图，展开 Bottom-Up 视图按 Total Time 排序；
  3. Memory 面板录制前后各拍一次堆快照，用 Summary 视图对比对象总数。

判读要点：

  • 主线程有没有 Long Task（超过 50ms 的任务块）。本 demo 的负载量级（8 台设备、3~15s 一报、图表 800ms 一刷）不应出现明显长任务；
  • 若有，优先怀疑两处：ECharts setOption 的数据量（滑窗 120 点是刻意设的上限，别在演示时随手调到 10000）与对大数组的深层响应式 watch；
  • 堆快照对比确认长会话没有持续增长——滑窗裁剪、告警 200 条上限、指令日志 20 条上限都是为此设计的，快照前后差值应稳定在一个小范围内。

最佳实践与常见坑 ​

坑 1：改了契约只改一端。 现象：某类报文「无声消失」——无报错、无警告，曲线/告警/回执就是不来。 原因：主题或字段只改了前端或只改了模拟器，parseTopic 正则不匹配返回 null，route 里 if (!info) return 静默忽略；或字段类型对不上被 codec 丢弃并计入「丢弃」计数。 解法：契约的单一事实来源收拢在 types/iot.ts + topics.ts（注释即契约文档），两端改动必须同批提交；用 mosquitto_sub 对照真实主题；改完跑一遍 3.6.1 的验收清单。

坑 2：把排查寄托在刷新页面。 现象：出问题就 F5，「好了」，过一会儿又坏；根因永远找不到。 原因：刷新会重建全部 store、清空 codec 统计与 pending 指令、重放 retained 档案——它一次性「洗掉」了几乎所有现场，偶发的时序问题被掩盖而非修复。 解法：先取证再动手。Console 报错、WS 帧面板、server 日志三处证据拿全，至少确定断点在哪一段，才允许动页面。

坑 3：只盯浏览器日志，不查服务端。 现象：在前端反复打断点、加日志，毫无头绪。 原因：MQTT 链路是设备 → Broker → 前端三段，前端只能看到「到达自己」的部分；报文根本没发出来、或 Broker 没转发到位，前端再怎么查也是空。 解法：先分段。mosquitto_sub 或 broker 日志确认报文是否存在，再决定查上游还是下游。

实操任务 ​

人为制造一个故障：改错订阅通配符，再用排查表把它找回来。

步骤：

  1. 打开 src/services/mqtt/topics.ts，把订阅清单改成只订阅遥测：

// 文件: demo/src/services/mqtt/topics.ts（故意改错，练完请恢复）
export const SUBSCRIBE_TOPICS = ['iot/+/+/up/telemetry'] as const

运行方式：保存后 vite 热更新自动生效（若未生效手动刷新一次页面——注意这次刷新是你已经观察完现场之后的动作）。

  1. 先预测再观察：这张订阅清单丢了 up/status、up/event、down/command_reply。对照 3.6.2 排查表，写下你预测会出现的现象，再逐一验证——至少应观察到：卡片档案缺失（无名称/产品信息）、告警中心不再出现「设备上报」来源的记录、所有指令一律「超时」。
  2. 用排查表定位：现象横跨「卡片不出现」「告警不弹」「指令超时」三行，共同原因指向订阅范围——用 WS 帧面板证实：前端确实收到了 telemetry 帧，但没有任何 status / event / command_reply 帧；再用 server 日志证实这些报文 Broker 侧一直有发。断点锁定在「前端订阅」这一段。
  3. 恢复并回归：把订阅清单恢复为 ['iot/+/+/up/#', 'iot/+/+/down/command_reply']，重跑 3.6.1 验收清单中的档案、告警、指令三条。
  4. 写一份复盘：五句话记录「现象 / 预测 / 证据 / 根因 / 预防手段」。这个故障的教训恰恰是坑 1 的正面教材——订阅清单就是前后端契约的一部分，改它和改报文字段一样危险。

运行方式：全部完成后 pnpm typecheck 与 pnpm lint 走一遍，确认 topics.ts 恢复原状无残留改动。
