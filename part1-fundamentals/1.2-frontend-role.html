1.2.2 职责边界：前端不做什么 ​

初学者最容易犯的错误，是按"Web 开发"的惯性把前端当成全能层。以下三件事，请明确划出边界：

前端不做的事为什么不做谁来做demo 的分界
不直连设备的 TCP/UDP浏览器没有原生 TCP socket；出于沙箱与混合内容安全模型也不允许。设备侧的 TCP/TLS 接入只能由设备 SDK 或网关完成设备 SDK / 边缘网关设备走 TCP 1883，前端只能走 WebSocket 8083
不承担协议编解码的最终责任报文契约是设备与平台之间的协议；前端只做"展示前校验"，发现坏数据丢弃即可，没有资格也没有能力"修正"契约平台 / 设备固件codec.ts 把解码收敛为一层：校验、按 mid 去重、时钟纠偏（漂移超 5 分钟钳制为本地时间），UI 层零容错代码
不做海量数据存储与规则引擎时序数据的存储、降采样、跨设备联动计算，量级远超浏览器内存与生命周期；"温度超 35℃ 告警"这类规则若在前端跑，页面一关规则就消失时序数据库 / 平台规则引擎前端只保留 windowCap = 120 点的滑动窗口（config.ts）；告警三条来源中，平台规则引擎那一路 demo 未启用

一句话总结边界：前端负责"人与物的界面"，不负责"物与物的基础设施"。浏览器的能力边界（无原生 TCP、内存有限、生命周期随页面）决定了这些事做不了；安全边界（不持有设备密钥、不经手原始遥测的最终存储）决定了这些事不该做。

"不做"不是"不存"。前端照样要在内存里维护一份近期数据供界面消费——关键是它必须是有界的。看 demo 滑动窗口的裁剪逻辑：

ts
// 文件: demo/src/stores/devices.ts（节选）
// 遥测入库：只保留最近 windowCap=120 个点，防止长会话内存无限增长
for (const p of points) e.window.push(p)
if (e.window.length > CONFIG.windowCap) {
  e.window.splice(0, e.window.length - CONFIG.windowCap) // 一次性裁掉最旧的多余点
}

// 文件: demo/src/services/mqtt/codec.ts（节选）
// Result 风格返回值：调用方无需 try/catch，坏报文在这里被拦下
export type DecodeResult<T> = { ok: true; value: T } | { ok: false; reason: string }

// 数值清洗：字符串数字兜底转换，其余非有限数一律剔除，绝不让 NaN 流进图表
function num(v: unknown): number | undefined {
  if (typeof v === 'number' && Number.isFinite(v)) return v
  if (typeof v === 'string' && v.trim() !== '' && Number.isFinite(Number(v))) return Number(v)
  return undefined
}

注意"不做"不等于"不了解"。前端必须理解 Broker 的转发语义、Topic 契约和 QoS 含义，才能设计出正确的界面状态（比如 1.1 章的指令三态）。你划出去的是实现，不是知识。

最后用一张"Web 直觉 vs IoT 实际"对照表收尾，这几条误区几乎每个转行做 IoT 前端的人都踩过：

Web 开发直觉IoT 实际demo 的做法
"数据丢了就重拉一次接口"设备上报是推流，没有"重拉"；丢包靠 QoS 与补发语义兜底遥测 QoS 0 丢了就丢了，下一条 4~8 秒内就来
"接口报错要 toast 提醒用户"每秒多条消息，逐条弹窗等于拒绝服务坏报文静默丢弃，计数累加在连接指示器里
"状态存组件里就行"消息流按设备 id 高频写入，且要跨页面共享Pinia store 以 Record<deviceId, Entry> 收敛
"轮询一下最简单"高频遥测下轮询既慢又贵，还拿不到下行能力实时通道走 MQTT over WebSocket（第 1.3 章）

1.2.3 两条接入路径：经平台 API vs 直连 Broker ​

确定职责后，下一个决策是：前端的实时数据从哪里来？两条主流路径：

text
// 图示：前端接入设备的两条路径
路径 A：经平台 API（拉取 + 推送）
  设备 ── MQTT ──▶ 云平台 ──┬── REST/GraphQL（前端轮询，秒~分钟级）
                            └── SSE/长轮询（服务端单向推，秒级）
                            ────▶ 前端

路径 B：前端直连 Broker（demo 采用）

                 （平台职责被 aedes 简化：只剩按 Topic 转发）

维度路径 A：平台 API（轮询/SSE）路径 B：直连 Broker（MQTT over WebSocket）
实时性轮询秒~分钟级；SSE 秒级推送，毫秒~秒级
通信方向请求-响应；SSE 单向全双工（可上行可下行）
鉴权成熟：API 网关、Cookie/JWT 统一管Broker 凭证需平台另行签发短时 token
订阅粒度按 API 资源，一次拿一批Topic 级，可用通配符精细订阅
历史数据/快照天然擅长（查询接口）Broker 不存历史；demo 靠 retain 消息部分弥补
服务端成本高频轮询压力大消息压力在 Broker，API 侧轻
浏览器适配原生支持需 Broker 开 WS 入口（见第 1.3 章）
典型场景管理后台、报表页、城市级海量设备监控台、实时大屏、设备数可控的园区级系统

demo 选择路径 B，理由有三：其一，8 台设备全量订阅毫无压力，Topic 通配符 iot/+/+/up/# 一句话收齐上行；其二，双向是刚需——控制指令要从同一条连接发下去；其三，教学上最能暴露 MQTT 的真实语义（QoS/retain/LWT 全都亲历）。

生产系统最常见的是混合模式：历史曲线、设备列表分页走 REST（快照），实时增量走 MQTT over WebSocket（推流），互为补位。demo 里 retain 的 status 消息在订阅瞬间回放设备档案，相当于 Broker 替你做了半个"快照接口"；而完整的时序历史，demo 用 120 点滑动窗口代替——这两个取舍你要能讲清楚。

选路径 B 时有一件事必须由平台侧配套：凭证签发。浏览器不应持有设备的 MQTT 用户名密码，正确做法是前端先向平台 API 换取短时 token，再凭它连接 Broker；demo 为了教学简化，本地 Broker 完全开放（无鉴权），这一点在生产环境不可照搬。

前端怎么接入这条链路？demo 用了一个"装配层"把无框架依赖的服务层接进 Pinia：

ts
// 文件: demo/src/composables/useIot.ts（节选）
// 网关不 import 任何 store——依赖全部通过回调注入，服务层保持可单测
const gateway = new IotGateway({
  onConnectionState: (state, attempt, detail) => conn.set(state, attempt, detail),
  onProfile: (deviceId, productId, s) => devices.ingestProfile(deviceId, productId, s),
  onTelemetry: (deviceId, productId, points) => devices.ingestTelemetry(deviceId, productId, points),
  onEvent: (deviceId, productId, ev) => alerts.pushEvent(deviceId, devices.nameOf(deviceId, productId), ev),
})
gateway.start()
devices.startWatchdog() // 前端离线看门狗：兜底 status 报文丢失等"静默故障"

对照着看，四大职责在 demo 里的"厚薄"并不均匀：③ 告警处置的界面最多（横幅、中心、徽标、事件流四处落点），④ 配置只有一个切片。这种不均衡本身就是教学设计——把最能体现"实时双向"特性的 ②③ 做厚，最适合前端建立手感。

按下面的顺序操作，每一步都对应一个职责：

  1. ① 可视化：进入"设备列表"，应看到 8 台设备卡片秒出（retain 回放档案）；点进 gh01-001，曲线每 4~8 秒向右生长一个点。
  2. ② 控制：进入 pl01-001（智能插座）详情页，点"开关"按钮——按钮变为"执行中"（pending），约 300ms 后日志区变为"成功"（ok），开关状态翻转；随后曲线上的功率归零或回升。
  3. ③ 告警：等 gh01-003 偶发温度尖峰，侧边栏徽标 +1，顶部弹出告警横幅；进入"告警中心"点"全部确认"，徽标清零。
  4. ④ 配置：在 gh01-001 详情页把温度阈值改为 25（合法范围 [20, 60]），观察指令日志回执"温度阈值已更新为 25℃"；再尝试改成 80，应看到"被拒绝"（rejected）。
  5. 离线剧本：回到列表页静候，约 40 秒后 gh01-006 计划内下线，应弹出 warn 级"设备离线（graceful_shutdown）"。
  6. 连接可视化：全程观察侧边栏底部的连接指示器——连接五态的切换，以及"收到/解码/丢弃/重复/纠时"五个解码计数的变化（重复计数增长，说明设备在重发脏报文，见 1.2.2 的解码层）。

最佳实践与常见坑 ​

  • 现象：指令点了没反应，用户连点五次，设备收到五条重复指令。 原因：指令回执有真实时延（demo 里是 300ms 模拟，真机可能数秒），界面若不呈现"执行中"状态，用户必然重试。 解法：按钮点击即进入 pending 并禁用，以回执 id 关联 Promise（ControlPanel.vue 的 logs 数组），ok/rejected/timeout 三态分别给出明确文案；timeout 后允许重试而非自动重发。

  • 现象：监控台开一天后越来越卡，内存持续上涨。 原因：遥测无限堆积进组件状态，且每个点都触发一次全量重绘。 解法：三件套——滑动窗口定长裁剪（windowCap）、图表增量 append、渲染节流合并高频帧。把"存多少"收敛在 store 一处，别散在组件里。

  • 现象：开两个浏览器标签页联调，两边互相提示掉线。 原因：MQTT 规定同一 clientId 的两个连接互踢；若 clientId 写死，两个标签页就成了"同一个客户端"。 解法：clientId 加随机后缀（demo：web-console_xxxxxxxx，见 connection.ts）；同时意识到每个标签页一条连接的规模隐患，必要时改用服务端汇聚后经 SSE 广播。

  • 现象：设备断网瞬间告警中心被刷屏，恢复后又来一波。 原因：把每次"错过上报"都当成离线事件告警，且没有去重窗口。 解法：同设备同 code 在冷却窗口内只收第一条（demo 为 60 秒，见 stores/alerts.ts）；离线告警用 offlineAlerted 标志保证一次离线只报一次；列表设容量上限（demo 200 条）防长会话膨胀。

  • 现象：曲线上偶现"回跳"的旧点，或温度突然跳回几分钟前。 原因：demo 特意制造的脏数据剧本——约 6% 概率原样重发上一条遥测（mid 相同），低功耗批量样本带约 90 秒的设备时钟偏移。 解法：解码层按 mid 去重；时间戳漂移超过阈值就钳制为本地接收时间（见 codec.ts）。容错收敛在解码层一处，曲线永远单调向前，UI 层不用写一行补丁。
