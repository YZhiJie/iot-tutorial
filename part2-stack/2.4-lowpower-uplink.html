学习目标 ​

  • 理解低功耗设备"批量 + 稀疏"上报的省电逻辑，以及它给前端制造的三个新麻烦
  • 能设计并解析 { mid, ts, samples } 批量信封
  • 掌握 codec 层四件套：单包/批量双形态识别、时间戳漂移钳制、mid 去重、字段级校验
  • 理解遥测报文用 QoS 0 的取舍，知道哪些消息必须 QoS 1

为什么"批量 + 稀疏"上报 ​

低功耗设备（NB-IoT、LoRa 终端等）靠电池运行几个月甚至几年，功耗预算的分配极其苛刻：射频发射是最耗电的动作，远高于 CPU 运算。所以典型工作模式是——平时深度睡眠（微安级电流），定时唤醒采一次样存进本地缓存，攒够一批才唤醒射频，一次性发出。

对报文形态的直接影响：

  • 稀疏：上报周期长（demo 低功耗剧本是 15 秒一包，真实 NB-IoT 设备可能是分钟级甚至小时级），数据不再"匀速流"，而是脉冲式到达。
  • 批量：一包里塞多个历史采样点（demo 是 4 个、缓存间隔 30 秒），单包多值。
  • 时间戳不可全信：设备为了省电常用廉价时钟，还会在深睡中累计漂移——报文里的时间戳可能整体偏移（demo 刻意造了 +90 秒的偏移）。

对照 demo 的 gh01-002「育苗棚 A2 · 温湿度（低功耗）」剧本，模拟器这样制造数据流：

js
// 文件: demo/server/simulator.mjs（节选：lowpower 剧本循环）
/** 低功耗剧本：15s 深睡，醒后把缓存 4 个样本一次性上报（带轻微时钟偏移） */
function startLowPowerLoop(client, state) {
  return jitterLoop(15000, 15000, () => {
    const samples = []
    for (let i = 3; i >= 0; i--) {
      stepSensor(state)
      samples.push({
        // +90s 模拟设备时钟偏移（在容忍范围内，前端应保留原值）
        t: Date.now() + 90_000 - i * 30_000,
        temp: round1(state.temp),
        humi: round1(state.humi),
        battery: Math.round(state.battery),
      })
    }
    const payload = { mid: mid(), ts: Date.now(), samples }
    state.lastTelemetry = payload
    publish(client, `${state.base}/up/telemetry`, payload)
    console.log(`[device] ${state.def.id} 批量上报 ${samples.length} 个缓存样本`)
  })
}

设计要点三条：

  1. mid 放在信封层，不放样本层：去重的单位是"一次射频发送"。同一个批量报文在网络里重传/重发时，4 个样本要一起判重；反过来不同批量之间不存在重复样本。信封级 mid 一票管整包。
  2. 每个样本自带时间戳 t：批量里的点是分散在过去的 30 秒缓存间隔上采的，信封层的 ts 只代表发送时刻。没有样本级 t，这 4 个点的真实时间关系就丢了。
  3. battery 必带：低功耗运维的第一指标是"还剩多少电"，哪怕省掉 rssi 也要带上它。

codec：把不可信的批量报文变成可信数据点 ​

codec.ts 的头注释是整章的题眼："网络对端是不可信的：JSON 可能烂、字段可能缺、时间戳可能漂、报文可能重复。本层统一负责：解析 → 校验 → 归一化 → 去重 → 统计打点。"批量信封的解析全部收敛在 decodeTelemetry 一个函数里：

ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
export function decodeTelemetry(payload: unknown, recvTs: number): DecodeResult<TelemetryPoint[]> {
  codecStats.received++
  const parsed = parseJson(text(payload))
  if (!parsed.ok) {
    codecStats.dropped++
    return parsed
  }
  const obj = parsed.value

  // 去重：以报文 mid 为准；缺 mid 的报文无法去重，仍照常处理
  const id = typeof obj.mid === 'string' ? obj.mid : null
  if (id && !markSeen(id)) {
    codecStats.duplicates++
    codecStats.dropped++
    return { ok: false, reason: '重复报文' }
  }

  // 批量信封 → 展开为多个遥测点
  if (Array.isArray(obj.samples)) {
    const points: TelemetryPoint[] = []
    for (const s of obj.samples) {
      if (!s || typeof s !== 'object' || Array.isArray(s)) continue
      const p = normalizeSample(s as Record<string, unknown>, recvTs)
      if (p) points.push(p)
    }
    if (points.length === 0) {
      codecStats.dropped++
      return { ok: false, reason: '批量信封内无有效样本' }
    }
    codecStats.decoded++
    return { ok: true, value: points }
  }

  // 单包
  const p = normalizeSample(obj, recvTs)
  if (!p) {
    codecStats.dropped++
    return { ok: false, reason: '无有效遥测字段' }
  }
  codecStats.decoded++
  return { ok: true, value: [p] }
}

时间戳漂移钳制 ​

每个样本过 normalizeSample 时，时间戳要过一道纠偏：

ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
/** 时间戳漂移容忍：偏差超过 5 分钟视为设备时钟异常，钳制为本地接收时间 */
const MAX_TS_DRIFT_MS = 5 * 60 * 1000

function fixTs(raw: unknown, recvTs: number): { ts: number; corrected: boolean } {
  const ts = num(raw)
  if (ts === undefined) return { ts: recvTs, corrected: true }
  if (Math.abs(ts - recvTs) > MAX_TS_DRIFT_MS) return { ts: recvTs, corrected: true }
  return { ts, corrected: false }
}

阈值取 ±5 分钟是有讲究的：批量缓存样本天然"滞后"于发送时刻，轻微偏移是常态（demo 的 +90 秒偏移就在容差内，被原样保留，corrected: false）；但偏移超过 5 分钟就只能认定为设备时钟坏了，用本地接收时刻顶替并打 corrected 标记。如果阈值卡得太紧（比如 ±10 秒），所有缓存样本都会被错标成"当前时刻"，整条曲线被压成一团——历史信息全丢。

mid 去重：500 容量环形淘汰 ​

去重不能无限存历史 id，demo 用 Set + 队列做定容淘汰（近似 LRU）：

ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
const seenMids = new Set<string>()
const midQueue: string[] = []

/** 首次出现返回 true；已见过返回 false（即重复报文） */
function markSeen(id: string): boolean {
  if (seenMids.has(id)) return false
  if (midQueue.length >= DEDUPE_CAP) {          // DEDUPE_CAP = 500
    const oldest = midQueue.shift()
    if (oldest !== undefined) seenMids.delete(oldest)
  }
  midQueue.push(id)
  seenMids.add(id)
  return true
}

字段级校验：绝不让 NaN 流入 UI ​

样本字段逐个清洗，字符串数字兜底转换，其余非有限数一律剔除：

ts
// 文件: demo/src/services/mqtt/codec.ts（节选）
/** 数值字段清洗：字符串数字兜底转换，其余非有限数一律剔除，绝不让 NaN 流入 UI */
function num(v: unknown): number | undefined {
  if (typeof v === 'number' && Number.isFinite(v)) return v
  if (typeof v === 'string' && v.trim() !== '' && Number.isFinite(Number(v))) return Number(v)
  return undefined
}

前端聚合展示与 QoS 0 取舍 ​

批量样本展开逐点入滑窗 ​

解码出的 TelemetryPoint[] 经网关回调进入 store，整批 push 进滑动窗口：

ts
// 文件: demo/src/stores/devices.ts（节选）
function ingestTelemetry(deviceId: string, _productId: string, points: TelemetryPoint[]): void {
  if (points.length === 0) return
  const e = ensure(deviceId)
  if (!e.online) {
    e.online = true // 遥测到达即视为在线（status 报文丢失的兜底）
    e.offlineAlerted = false
  }
  // lastSeen 用本地接收时刻：设备时钟可能漂移，不能信它的时间戳
  e.lastSeenAt = Date.now()

  for (const p of points) e.window.push(p) // 批量样本逐点入滑窗
  const last = points[points.length - 1]
  if (last) e.latest = last // 卡片上的"最新值"取批内最后一个

  // 滑窗裁剪：一次性删除超出上限的最旧数据
  if (e.window.length > CONFIG.windowCap) {
    e.window.splice(0, e.window.length - CONFIG.windowCap)
  }
}

QoS 0 的取舍 ​

模拟器发遥测时没有指定 qos（publish 默认 qos 0），这不是偷懒而是取舍。对照 topics.ts 的契约注释：

ts
// 文件: demo/src/services/mqtt/topics.ts（节选：契约注释）
//   up/telemetry        设备 → 云   遥测数据            QoS 0（高频可容忍丢失）
//   up/status           设备 → 云   在线状态/设备档案   QoS 1 + retain（保留消息）
//   up/event            设备 → 云   异常事件（告警）    QoS 1
1
2
3
4

遥测用 QoS 0 的理由：下一批 15 秒后就到，丢一包曲线缺一个点，无伤大雅；而 QoS 1 的"至少一次"语义必然带来重复报文（重传 + PUBACK 往返），去重压力反而更大，设备侧还要维护报文 id 状态、多耗电。指令、状态、事件必须 QoS 1——丢一条开关指令是业务事故。一句话：按消息的业务代价定 QoS，不是越高越好。

最佳实践与常见坑 ​

坑 1：new Date(设备时区字符串)

  • 现象：设备报文里时间给的是 '2026-10-18 09:30:00' 这类字符串，Chrome 按本地时区解析出来，Safari 直接得到 Invalid Date——同一份数据不同浏览器曲线对不上。
  • 原因：非 ISO 8601 格式字符串的解析行为是未定义的，且字符串本身丢失了时区语义。
  • 解法：契约规定时间戳一律传 epoch 毫秒数（demo 的 t / ts 都是数字）；字符串只在展示层由 new Date(数字) 格式化，绝不让设备直接传时间字符串。

坑 2：样本时间戳倒序未排序

  • 现象：个别固件把缓存倒序发出，曲线折返打结；latest 取到的是批内最后一个点，结果是最旧的那个样本。
  • 原因：codec 展开后按到达顺序 push，而 store 的 window 假定时间升序——"假定设备友好"是靠不住的。
  • 解法：批量展开后在解码层排序（上文文档示例的 points.sort((a, b) => a.ts - b.ts)），把"数据是干净的"这保证收敛在 codec 一处，别指望每一层都防。

坑 3：把去重放在 UI 层

  • 现象：A 页面做了去重、B 页面没做；重复报文计数缺失；新加一个视图又要抄一遍 Set 判重逻辑。
  • 原因：去重属于"不可信数据归一化"，散在 UI 必然漂移，而且 UI 组件随路由销毁重建，去重状态根本留不住。
  • 解法：codec 层 markSeen 统一去重（模块级单例，页面怎么切状态都在），UI 拿到的永远是干净数据；codecStats 顺带给出可观测性。

坑 4：把批量信封当单包解析

  • 现象：解析器只读顶层字段，samples 被当成无关字段忽略，整包被判"无有效遥测字段"丢弃；或只画出一个点，丢了 3 个。
  • 原因：解析逻辑只覆盖单包形态，低功耗设备上线后数据"神秘消失"。
  • 解法：codec 做双形态识别（Array.isArray(obj.samples)），并且让批量与单包共用同一个 normalizeSample，两种形态产出同构的 TelemetryPoint[]。

实操任务 ​

  1. 越过钳制阈值：把 simulator.mjs lowpower 剧本的 90_000 改为 10 * 60 * 1000（10 分钟，超出 ±5 分钟容差），重启 pnpm server，观察：hover 曲线时间不再超前本地时钟（时间戳被接收时刻顶替）、批量样本被压到同一时刻附近；改回 90_000。
  2. 全量重发实验：把 simulator.mjs 里重发概率 Math.random() < 0.06 临时改为 Math.random() < 1（每条必重发），重启后观察「丢弃」计数暴涨而曲线依旧平滑——去重整包拦截，UI 毫发无伤；改回 0.06。
  3. 加字段零改动：给 lowpower 剧本的样本 push 里加一个 rssi: Math.round(state.rssi) 字段，重启模拟器。codec 的 METRIC_KEYS 已包含 rssi，字段级校验自动放行——前端零改动就能带上新字段，体会"归一化收敛在一处"的好处。

验收标准 ​
